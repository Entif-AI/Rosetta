# Projection provenance v1 (proposed fixture contract)

An additive support handle for existing materialized views, not another semantic authority. Each handle binds the exact source record, manifestation, canonical artifact, lineage, policy, scope and rights references; exact observation spans retain the current Core offset convention (UTF-16 code units), and receipts retain their native identity. Content hashes do not establish source identity or independent testimony.

The bounded inspector resolves native tiles and raw text only after the supplied authority permits the entire constituent set. Every native manifestation access requirement must match the canonical artifact rights scopes, and the selected scope must belong to that set. An observation must name the exact canonical artifact in its native parents; a receipt must carry that exact artifact in its native subject or claim evidence. Before any raw hydration, the inspector checks all constituents, native tile integrity, normalized text hashes, source and manifestation linkage and receipt verification. Raw source and span hashes and projection correspondence are also verified. Missing, stale, conflicting or unauthorized support produces the same unavailable result. Cumulative raw text bytes, encoded support tile bytes, projection bytes and planned tile lookups have separate explicit limits. Storage callbacks receive remaining byte budgets and must enforce them before returning data; defensive post-return checks are not a remote I/O or memory guarantee. Current rights and lifecycle are checked again before hydration and before returning support.

Vector chunks and lexical shadows remain non-authoritative recall; temporal edges remain temporal projections; scores remain activation. A tag or summary can carry truth support without acquiring truth authority. Identity-sensitive support requires policy and authorization evidence; unknown classification fails closed. Rebuildability declares source and operational dependencies, or reasons why replay is impossible. Restoration, semantic revalidation and authorized use are separate. A safe hold never permits writes; every other write routes through the existing admission owner.

Exact replay preserves an immutable record identity. Any new revision must name its exact predecessor, keep the stable projection reference, use a distinct revision reference and advance observation time. It requires fresh revalidation even when byte content is unchanged. A non-replayable record cannot serve as a rebuild candidate.

The native Receipt helper in the existing receipts package runs the inspector against an exact action and submitted projection bytes. Before resolving support, the existing action/receipt owner must positively verify the binding of the native Action CID, exact operation, canonical submitted-record digest, optional submitted-predecessor digest and projection byte digest. A valid but unrelated Action is refused without issuing a trace attributed to it. The binding is checked again before receipt creation. The trace binds these exact request coordinates by digest, including for a structurally invalid but JSON-representable submitted record; it emits creation-candidate, rebuild-candidate, rejection, current inspection and invalidation-required claims. Refusal omits source evidence references; the trace remains protected audit evidence and is not an outward status envelope. The receipt-support verifier must establish issuer authenticity and substantive suitability for the exact handle and projection plane, not merely receipt integrity or the existence of a matching subject: evidence of a denial may support an observed denial, but cannot by itself support a positive claim. Active or unknown safe hold refuses creation and rebuild candidates while permitting bounded read-only inspection. No successful trace authorizes or attests a durable effect.

This is read-only fixture conformance, not a ratified authority, a distributed settlement protocol or an independently authenticated publisher. Production resolution must supply current, independently verified authority and a release fence; a final sequential check alone cannot exclude concurrent withdrawal. Signed receipt issuance, authorized lifecycle audit and actual rebuild execution remain owned by their existing interfaces.
