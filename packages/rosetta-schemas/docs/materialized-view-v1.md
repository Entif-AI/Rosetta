# Materialized view identity and currency v1

Public authority: #1731 under #1567, reusing executable #1730/#1560 impact/revalidation, #1558 temporal/knowledge roles, #1559 exact locks and #1551/#1553 migration/compatibility references. Source/provenance, rights/policy and canonicalization remain governed by their existing owners. This derived metadata Profile adds no Core kind or cache/refresh/ranking algorithm.

`materialized.view.v1` 1.0.0 records family, source identity/version/CID, known or unknown frontier/cursor/snapshot, event and observation windows, knowledge frontier, Core version, dependency locks, translator/migration revisions, policy/rights/tenant/workspace, transformation identity/configuration, dataset revision, canonicalization/conformance, materialization time, output reference/CID/digest and currency. Metadata identity is the SHA-256 of its canonical body; output content identity remains separate and must be checked by its artifact authority.

Public conformance requires the published shape plus `parseMaterializedView`. Source/dependency/policy staleness requires support. Unknown source frontier cannot claim current. Partial staleness carries bounded scope resolved against embedded impact evidence. Invalidation/revalidation reuses #1730, including its refusal to treat rebuild as validation. A current impacted artifact requires attributable PROVEN_UNAFFECTED or REVALIDATED_VALID evidence for its own subject. Supersession preserves replacement references.

`appendMaterializedView` preserves old metadata identities. New rematerializations explicitly supersede prior records of the same family; a new materialization time or compiler/model revision has a distinct identity even if source bytes are unchanged. Invalidated/partially stale prior material cannot return to current through remint alone: prior subject revalidation remains required. History is never sorted by timestamps or rewritten.

`admitMaterializedViewReuse` takes consumer requirements and a current rights decision from their owning authorities. It strictly requires boolean permission and a decision reference, including historical reads. When current evidence is required, it checks declared frontier and the complete required environment, including transformations, Core, locks, migration, dataset, scope, policy and rights revisions. Historical inspection is explicit and still subject to current rights. This function does not authenticate a supplied decision or grant effect/write/promotion authority.

Byte-validity does not imply currency. CURRENT_FOR_DECLARED_FRONTIER is relative to a supplied frontier/environment, never global freshness. Revocation can fence retained bytes without mutating history. Cases in `materialized-view.spec.ts` exercise all twelve required scenarios, plus malformed truthy rights, advanced transformations, incomplete impact scope and immutable history. No private reuse policy, scheduler, query planner or storage engine is implemented.

Build the owner, run focused/owner checks, then `node tools/view-integrity/schema-sync.mjs`. The shape references the published impact schema; include that schema when validating externally.
